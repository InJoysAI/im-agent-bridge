## 1. 产品概述（Product Overview）

### 1.1 背景与机会

本项目定位为一个 **通用多 IM AI 接入骨架**，不是某个单一垂直业务产品，也不是完整客服平台。它的目标是先搭建一条稳定、轻量、可复用的消息闭环，把外部 `IM` 渠道消息接入到 `AI Agent Runtime`，再通过真实工具完成响应并回写到原渠道。

现实场景中，很多 Agent、MCP、RAG、Workflow 系统已经具备一定执行能力，但缺少一层足够简洁的`IM 接入骨架`，导致不同业务在接 Telegram、WhatsApp、Discord 等消息入口时需要重复建设。现有方案通常分为三类：

* 只解决消息桥接，不解决 Agent 调用与工具执行
* 只解决 Agent / Runtime，不提供 IM 接入主链路
* 平台能力过重，不适合做第一版最小闭环验证

因此本项目的切入方式是：

**先以 Telegram 为首个验证渠道，聚焦消息收发、Agent 调用、真实工具调用和回复回写，验证最小链路成立。**

* **市场现状：** 多数现有方案在 IM 接入、Agent 调用与工具能力之间缺少统一骨架。
* **目标用户痛点：**

  1. 不同 IM 渠道接入成本高，重复建设严重。
  2. Runtime 与工具调用体系不统一，难以复用。
  3. 第一版系统常常因平台化设计过重而落地缓慢。
* **竞品分析摘要：**

  1. 消息桥接类方案缺少 Agent 执行闭环。
  2. Agent 运行时类方案缺少消息入口骨架。
  3. 完整客服 / 自动化平台过于复杂，不适合最小 MVP。
* **切入点：** 以三层架构为基础，先完成 `Telegram` → `Bridge` → `Gateway` → `Agent Runtime` → `Shopify MCP` → 回写 `Telegram` 的最小主链路。

### 1.2 核心价值主张

* **通用骨架：** 提供可复用的多 IM AI 接入主链路，而不是绑定单一业务。
* **轻量实现：** 第一版只保留最小核心链路，降低接入和迭代成本。
* **Runtime 可替换：** 支持轻量的 `Agent Runtime` 接入。
* **真实工具验证：** 第一版直接接入 Shopify MCP，验证真实工具执行能力。
* **可持续扩展：** 后续可扩展更多 IM、更多 `Agent Runtime`、更多业务工具，而不推翻骨架。

### 1.3 产品目标与成功指标

| 目标类型    | 指标                                     | 目标值   | 时间窗口     |
| ------- | -------------------------------------- | ----- | -------- |
| 功能可用性   | Telegram 文本消息接入成功率                     | ≥ 95% | MVP 联调阶段 |
| 回复闭环    | 回复回写成功率                                | ≥ 95% | MVP 联调阶段 |
| 工具调用    | Shopify MCP 成功调用率                      | ≥ 90% | MVP 联调阶段 |
| 架构可维护性  | 替换 Runtime 时无需修改 Channel / Bridge 核心逻辑 | 达成    | MVP 评审阶段 |
| 工程边界清晰度 | 固定三层架构与统一边界                            | 达成    | MVP 设计阶段 |

### 1.4 术语约定

| 术语            | 定义                                       | 备注                             |
| ------------- | ---------------------------------------- | ------------------------------ |
| IM            | 即时通讯渠道，如 Telegram、WhatsApp、Discord、Slack | 本文档第一版仅涉及 Telegram             |
| Channel Layer | 承载用户消息入口与回复出口的渠道层                        | 如 Telegram                     |
| Bridge Layer  | 负责连接 IM 与系统核心层的桥接层                       | 第一版采用 Matterbridge             |
| Core Layer    | 系统核心层，负责 Gateway、Runtime 调用与回写控制         | MVP 核心                         |
| Gateway       | Core Layer 的统一对外入口                       | Bridge 只对接 Gateway             |
| Runtime Agent | Core 内部执行器（又称 Agent Runtime），负责接收标准请求、调用工具、返回结果            | 第一版首选候选为 NanoBot               |
| MCP           | 工具能力接入协议或模式                              | 第一版使用 Shopify MCP              |
| Session       | 一次上下文会话的归属标识                             | Core 负责边界，Runtime 负责上下文记忆      |
| chat_id       | 渠道会话容器标识                                 | 用于来源识别与消息回写                    |
| chat_type     | 会话类型                                     | 如 private、group                |
| session_id    | Runtime 使用的上下文归属唯一标识                     | MVP 阶段不引入 thread_id 与 group_id |

## 2. 用户角色与流程（User Roles & Flow）

### 2.1 用户角色

| 角色名称     | 描述                     | 核心权限                   |
| -------- | ---------------------- | ---------------------- |
| 最终消息发送者  | 在 Telegram 中发送文本消息的用户  | 发送消息、接收回复              |
| 系统开发者    | 负责骨架搭建、Runtime 接入、工具联调 | 配置渠道、接入 Runtime、配置 MCP |
| 运维 / 维护者 | 负责服务部署、监控、问题排查         | 查看日志、调整配置、重启服务         |

### 2.2 核心用户路径

1. **发送消息：** 用户在 Telegram 中发送一条文本消息。
2. **消息接入：** Bridge Layer 接收到消息并发送到 Core Layer 的 Gateway。
3. **标准化处理：** Gateway 将原始消息转为统一消息结构。
4. **调用 Runtime：** Gateway 将标准请求传递给 Runtime Agent。
5. **调用工具：** Runtime Agent 根据请求调用 Shopify MCP。
6. **生成回复：** Runtime Agent 返回标准文本结果。
7. **回复回写：** Gateway 将结果回写给 Bridge Layer，再由 Bridge 层发回 Telegram 原会话。

### 2.3 关键用户场景

* **场景 A — Runtime 不可用：** 系统应返回明确错误提示，并记录日志。
* **场景 B — Shopify MCP 调用失败：** 系统应返回用户可理解的失败信息。
* **场景 C — 非文本消息：** 系统应忽略或提示当前仅支持文本消息。
* **场景 D — 回复回写失败：** 系统应记录日志并支持后续排查。
* **场景 E — 会话上下文延续：** 同一会话的多轮消息应保持基本上下文连续，但不引入重型会话系统。
* **场景 F — 私聊会话隔离：** 用户在 Telegram 私聊中发送消息时，系统应为该私聊维持独立 `session_id`，保证私聊上下文不与其他会话混用。
* **场景 G — 群聊共享会话：** 用户在 Telegram 群聊中发送消息时，MVP 阶段系统应按群聊维度复用共享 `session_id`，群内消息共享同一上下文。
* **场景 H — 群聊与私聊并存：** 同一用户在群聊和私聊中分别向系统发起请求时，系统必须将其视为两个独立上下文，不能相互污染。
* **场景 I — 数据库不可用：** PostgreSQL 不可达时，系统应返回统一错误提示（如“系统暂时不可用，请稍后重试”），不允许在持久化失效状态下继续写入不一致会话，并记录系统级告警日志。

## 3. 功能需求说明（Functional Requirements）

### 3.1 Channel 接入模块（P0 - 核心）

第一版只支持 Telegram，且只支持文本消息。

#### 3.1.1 Telegram 文本消息接入

* **功能描述：** 接收 Telegram 用户发送的文本消息。
* **交互要求：** 用户无需使用额外前端界面，直接在 Telegram 完成交互。
* **逻辑要求：**

  * 第一版只支持 Telegram。
  * 第一版只支持文本消息。
  * 非文本消息不进入主处理链路。
* **验收标准：**

  * [ ] Telegram 文本消息可成功进入系统。
  * [ ] 非文本消息不会导致服务异常。

#### 3.1.2 原会话回复回写

* **功能描述：** 将处理结果回写到原 Telegram 会话。
* **输入/输出：**

  * 输入：Gateway 输出的标准文本回复
  * 输出：Telegram 可见文本消息
* **逻辑要求：**

  * 回复必须发送到原会话。
  * 第一版仅支持文本回复。
* **错误处理：**

  * 回写失败 → 记录日志并返回失败状态
  * 会话不存在或失效 → 记录错误并停止回写

---

### 3.2 Bridge 模块（P0 - 核心）

Bridge Layer 第一版采用 Matterbridge，职责仅为消息桥接，不承担业务逻辑。

#### 3.2.1 消息桥接

* **功能描述：** 接收 Telegram 消息并发送到 Core Layer 的 Gateway。
* **交互要求：** 对最终用户透明。
* **逻辑要求：**

  * Bridge Layer 不处理业务语义。
  * Bridge Layer 不直接调用 Runtime Agent。
  * Bridge Layer 仅与 Core Layer 的 Gateway 通信。
* **验收标准：**

  * [ ] Telegram 消息可稳定发送到 Gateway。
  * [ ] Bridge 配置变更不影响 Gateway 对内接口结构。

#### 3.2.2 回复回桥

* **功能描述：** 接收 Gateway 返回的标准回复并回写到 Telegram。
* **输入/输出：**

  * 输入：标准文本回复对象
  * 输出：Telegram 文本消息
* **逻辑要求：**

  * Bridge 层不更改业务语义。
  * Bridge 层仅负责转发与回写。
* **错误处理：**

  * 桥接通道异常 → 记录日志并返回失败状态
  * 渠道断连 → 触发重试或人工排查

---

### 3.3 Core Layer 模块（P0 - 核心）

Core Layer 是系统主控层，包含 Gateway 与 Runtime Agent 两个核心部分。

#### 3.3.1 Gateway 统一入口

* **功能描述：** 作为 Core Layer 对 Bridge Layer 的唯一入口，接收、标准化和转发消息。
* **交互要求：** 对用户无直接感知。
* **逻辑要求：**

  * Gateway 是 Core 对外唯一入口。
  * Bridge Layer 不直接调用 Runtime Agent。
  * Gateway 负责消息接收、标准化、分发和回写协调。
* **验收标准：**

  * [ ] Bridge 消息全部通过 Gateway 进入 Core。
  * [ ] Gateway 不依赖具体 Runtime 实现。

#### 3.3.2 消息标准化

* **功能描述：** 将 Bridge 层的原始消息转为统一消息结构。
* **交互要求：** 无前端交互要求。
* **逻辑要求：**

  * 标准消息对象至少包含：`event_id`、`platform`、`chat_id`、`chat_type`、`user_id`、`session_id`、`text`、`timestamp`、`bot_id`
  * `bot_id` 由 Gateway 根据 Bridge 入站消息中的渠道来源标识（`platform` / `bridge_gateway_name` / `bridge_channel_name`）查询 `channel_bindings` 解析得出，不由外部请求直接传入
  * 单条文本消息上限为 4096 字符（继承 Telegram 平台限制），超过时拒绝处理并返回提示（如“消息过长，请缩短后重试”），同时记录日志
  * `session_id` 为上下文归属唯一标识
  * 私聊：`session_id = telegram:private:{chat_id}`
  * 群聊：`session_id = telegram:group:{chat_id}`
  * 第一版不引入 `thread_id`
  * 第一版不单独引入 `group_id`
* **验收标准：**

  * [ ] 进入 Runtime 的消息结构统一
  * [ ] Runtime 不依赖 Telegram 原始协议格式
  * [ ] 私聊与群聊的上下文边界可被正确区分

#### 3.3.3 Runtime Agent 调用

* **功能描述：** Gateway 调用 Runtime Agent，传入标准输入并接收标准输出。
* **输入/输出：**

  * 输入：标准化消息请求对象
  * 输出：标准化文本回复对象
* **逻辑要求：**

  * Runtime 必须可替换
  * 第一版默认使用 NanoBot
  * Runtime 与 Gateway 通过适配层解耦
* **错误处理：**

  * Runtime 无响应 → 返回通用失败提示
  * Runtime 返回格式异常 → 记录日志并中断回写

#### 3.3.4 Shopify MCP 工具调用

* **功能描述：** Runtime Agent 根据用户请求调用真实 Shopify MCP 工具。
* **输入/输出：**

  * 输入：用户自然语言请求
  * 输出：Shopify MCP 返回结果，经 Runtime 组织为文本回复
* **逻辑要求：**

  * 第一版接真实工具，不走 mock 主链路
  * **MCP 实例管理**：MVP 阶段，MCP 实例通过 Agent Runtime 对应的 `MEMORY.md` 文档进行声明与管理，不通过数据库动态配置。
  * **凭证注入**：Shopify 的 API 凭证（Store URL, Shopify Client ID, Shopify Secret）通过 `.env` 或等效运行环境注入到对应 MCP 实例。
  * **隔离与路由**：Runtime 负责根据用户指令识别目标店铺，并调用对应的 MCP 实例，确保不同店铺间的业务逻辑隔离。
  * MVP 阶段默认启用当前运行环境中所有可用的 MCP 工具
* **错误处理：**

  * MCP 不可达 → 返回“工具暂不可用”
  * MCP 执行失败 → 返回用户可理解的失败信息

#### 3.3.5 文本回复组织

* **功能描述：** 将 Runtime 返回结果转换为统一文本回复对象。
* **交互要求：** 输出简洁、适合直接发回 Telegram。
* **逻辑要求：**

  * 第一版只输出文本
  * 不输出按钮、卡片、图片、文件或富媒体
  * 回复消息不得超过 4096 字符，超长时截断并附加截断提示
* **验收标准：**

  * [ ] 所有成功结果可统一转换为文本回复
  * [ ] 所有失败结果可统一转换为可理解提示

---

### 3.4 Runtime 适配模块（P0 - 核心）

第一版 Runtime 首选候选为 NanoBot。

#### 3.4.1 Runtime 候选与边界

* **功能描述：** 选择一个轻量 Runtime 作为第一版执行器。
* **逻辑要求：**

  * 第一版首选候选为 NanoBot
  * 使用其 Runtime、MCP、Memory、Provider 能力
  * 不使用其自带 Channel / Gateway 作为本系统主入口
* **验收标准：**

  * [ ] Runtime 可通过适配层被 Gateway 调用
  * [ ] Runtime 替换时不影响 Channel / Bridge 设计边界

#### 3.4.2 Runtime 统一适配接口

* **功能描述：** 提供统一输入输出接口，屏蔽 Runtime 差异。
* **输入/输出：**

  * 输入：标准消息请求对象
  * 输出：标准文本回复对象
* **逻辑要求：**

  * Gateway 只依赖接口，不依赖具体 Runtime
  * Runtime 选型变更不影响 Bridge 层
* **错误处理：**

  * 接口不兼容 → 在适配层解决，不向 Bridge 外溢

---

### 3.5 最小会话上下文能力（P1 - 重要）

#### 3.5.1 会话边界管理

* **功能描述：** Core Layer 负责会话边界定义与传递。
* **逻辑要求：**

  * Gateway 内部统一维护 session_id / chat_id / chat_type / user_id 作为标准消息上下文字段；接入 NanoBot 时，适配层至少需将 session_id / chat_id 映射到 NanoBot 的会话机制，chat_type / user_id 作为 Gateway 侧保留上下文信息，并按需要传递给 Runtime 提示词、工具调用上下文或扩展元数据。
  * `session_id` 作为上下文归属唯一标识
  * MVP 阶段采用：

    * 私聊独立上下文
    * 群聊共享上下文
  * 暂不支持群聊内按用户拆分上下文
* **验收标准：**

  * [ ] 同一私聊消息进入同一私聊上下文
  * [ ] 同一群聊消息进入同一群聊上下文
  * [ ] 私聊与群聊上下文彼此隔离

#### 3.5.2 上下文记忆管理

* **功能描述：** Runtime 负责最小上下文保留与使用。
* **逻辑要求：**

  * 上下文内容管理由 Runtime 提供
  * 上下文连续性以 `session_id` 为准
* **错误处理：**

  * 上下文丢失 → 允许退化为无上下文单轮处理

---

### 3.6 Core Layer 持久化需求（P0 - 核心）

#### 3.6.1 PostgreSQL 持久化

* **功能描述：** Core Layer 通过 PostgreSQL 实现关键数据的持久化存储。
* **逻辑要求：**

  * MVP 阶段引入 **PostgreSQL** 数据库，用于存储 session_id 映射关系、Bot 实例配置以及必要的上下文元数据。
  * 持久化由 Gateway 负责，Runtime 不强依赖数据库。
  * 所有 Bot 实例共享同一 PostgreSQL 实例，通过 `bot_id` 实现逻辑隔离。
  * 上下文元数据保留期不超过 30 天，由 PostgreSQL 定时任务（如 `pg_cron`）或应用层 Gateway 定期清理超期数据。
* **验收标准：**

  * [ ] Session 映射关系可正确持久化与查询
  * [ ] Bot 配置可正确读取
  * [ ] PostgreSQL 不可用时系统可返回统一错误提示

---

### 3.7 基础日志与错误追踪（P1 - 重要）

#### 3.7.1 关键链路日志

* **功能描述：** 记录主链路关键节点日志。
* **逻辑要求：**

  * 至少记录消息接入、Gateway 标准化、Runtime 调用、MCP 调用、回写结果
  * 日志需支持链路排查
* **错误处理：**

  * 日志系统异常 → 不得阻断主流程

## 4. 非功能性需求（Non-Functional Requirements）

### 4.1 安全性（Security）

| 需求项    | 描述                               | 目标          |
| ------ | -------------------------------- | ----------- |
| 渠道凭证保护 | Telegram、Bridge、MCP 凭证不得硬编码      | 使用环境变量或安全配置 |
| 接口边界控制 | Bridge 仅访问 Gateway，不直接访问 Runtime | 最小暴露面       |
| API 安全通信 | Bridge 与 Gateway 之间采用**安全 API 通信**（如 API Key/Token） | 防止未授权注入 |
| 工具调用约束 | Shopify MCP 工具权限由 Shopify 侧配置管理     | 权限边界不在本系统维护  |
| 配置隔离   | 每个 Bot 实例配置逻辑隔离（通过 bot_id 区分，共享 PostgreSQL） | 实现基础多租户隔离能力 |

### 4.2 性能（Performance）

| 指标             | 目标           | 度量方式                |
| -------------- | ------------ | ------------------- |
| 单条消息响应时间       | P95 ≤ 5 秒；hard timeout ≤ 15 秒        | 从消息接收到首条有效回复（5s 为正常场景目标，15s 为极端兆底）        |
| Runtime 调用超时   | ≤ 15 秒       | 单次 Runtime 调用最大等待时长 |
| Shopify MCP 超时 | ≤ 10 秒       | 单次工具调用最大等待时长（嵌套在 Runtime 超时内）        |
| 系统恢复性          | 单模块异常不导致整体崩溃 | 故障注入或联调验证           |

### 4.3 兼容性（Compatibility）

| 平台/环境          | 最低版本                  | 优先级 |
| -------------- | --------------------- | --- |
| Telegram       | Bot 接入环境可用            | P0  |
| Linux / Docker | Ubuntu 22.04+ 或等效容器环境 | P0  |
| Runtime 接口     | 支持本地适配调用或 HTTP 接口调用   | P0  |

### 4.4 可用性（Usability）

* 用户直接在 Telegram 中交互，无需学习额外界面。
* 第一版核心路径保持“一次输入，一次回复”。
* 错误必须可见，不能静默失败。
* 非文本输入需返回明确提示或安全忽略。

### 4.5 可维护性（Maintainability）

* 系统固定为三层架构：Channel Layer、Bridge Layer、Core Layer。
* Bridge 与 Gateway 解耦，Gateway 与 Runtime 通过适配层解耦。
* Runtime 可替换，不影响前两层架构边界。
* 关键配置项支持环境变量或配置文件管理。
* 日志必须覆盖主链路关键节点。
* 可观测性增强（统一 trace_id、业务指标采集）属于质量目标，MVP 阶段按需实现。

## 5. UI/UX 设计规范（UI/UX Guidelines）

第一版不提供独立图形界面，交互界面即 Telegram 会话窗口，因此本节以“消息交互体验规范”为主。

### 5.1 视觉风格

* **关键词：** 简洁、直接、低干扰、可读
* **配色方案：** 继承 Telegram 原生界面
* **字体：** 继承 Telegram 默认字体
* **图标风格：** 第一版无额外要求

### 5.2 交互原则

* 用户应通过自然语言直接触发系统能力。
* 回复应尽量短、清晰、可直接执行下一步。
* 出错时必须给出可理解提示。
* 第一版不使用命令式菜单作为主入口。

### 5.3 关键页面/状态清单

| Runtime 不可用状态 | 系统返回统一错误提示  | P0  |

## 6. 商业运营需求（Business & Operational Requirements）

### 6.1 运营位与引流

第一版不包含运营位与引流能力。

### 6.2 计费与付费

第一版不涉及计费、订阅、额度控制与支付。

### 6.3 数据与隐私

* **数据收集范围：** 仅收集必要运行日志与错误日志；消息内容可短期保留用于排障（截断存储，保留期不超过 30 天），不作为业务数据源
* **用户隐私策略：** 不建设独立用户画像体系；涉及 PII 的字段在落库时应脱敏或移除
* **合规要求：** 凭证不得明文暴露；消息仅用于本次处理链路，短期保留仅限排障用途

## 7. 技术约束与依赖（Technical Constraints）

| 约束/依赖        | 说明                  | 影响范围          |
| ------------ | ------------------- | ------------- |
| Telegram     | 第一版唯一渠道             | Channel Layer |
| Matterbridge | 第一版 Bridge Layer 实现 | Bridge Layer  |
| PostgreSQL   | 提供 Session 持久化与配置存储 | Core Layer    |
| Gateway      | Core Layer 对外唯一入口   | Core Layer    |
| 轻量 Runtime   | 第一版首选候选为 NanoBot    | Core Layer    |
| Shopify MCP  | 第一版真实工具依赖           | Core Layer    |
| Rust 技术栈       | Gateway 倾向使用 Rust 开发  | Core Layer    |
| 文本消息限定       | 第一版仅支持文本消息          | 全局            |

### 7.1 通信边界约束

1. **Bridge Layer 仅与 Core Layer 的 Gateway 通信**
2. **Bridge ↔ Gateway 外部通信采用 HTTPS**
3. **Gateway ↔ Runtime Agent 属于 Core 内部通信**
4. **Core 内部通信采用适配器模式，MVP 阶段不强制限定为 HTTPS**
5. **Runtime 不直接接管 Telegram 主入口**

### 7.2 Runtime 选型约束

* 第一版首选候选为 NanoBot
* MVP 中仅使用其 Runtime / MCP / Memory 能力
* **工具扩展能力**：MCP 实例通过 `MEMORY.md` 声明，凭证通过 `.env` 或等效运行环境注入，支持同时挂载多个独立启动的 MCP 实例。
* 不使用其自带 Channel / Gateway 作为主入口
* 若后续候选变化，不得影响三层骨架设计

## 9. 风险与对策（Risks & Mitigations）

| 风险描述                               | 概率 | 影响程度 | 应对策略                                    |
| ---------------------------------- | -- | ---- | --------------------------------------- |
| NanoBot 作为候选 Runtime 在当前场景下能力不完全匹配 | 中  | 高    | 通过适配器模式保留替换空间，不将其写死为不可替换核心              |
| Runtime 与 Bridge 边界混淆              | 中  | 高    | 明确 Runtime 不承担主入口职责，Bridge 仅对接 Gateway  |

| 会话上下文设计过重导致 MVP 膨胀                 | 高  | 高    | 只保留最小 session 边界与轻量上下文，不做独立记忆系统         |
| 后续需求扩展过快，破坏三层骨架                    | 高  | 高    | 严格锁定第一版为单渠道、文本消息、单 Runtime 主链路          |
| 群聊共享上下文可能导致多人提问时语义混淆               | 中  | 中    | MVP 阶段先采用群共享上下文，后续按实际使用情况决定是否升级为群内按用户拆分 |
